# ПОС

Преподавательская Оценка Студентов: консольный модуль оценивания с доменной моделью (DDD), архитектурой Ports and Adapters и паттернами GoF.

## Запуск

```sh
go run ./cmd/pos
```

Проверка:

```sh
go test ./...
```

В меню можно добавить студента, посмотреть студентов, добавить критерий (название, максимальный балл, вес), посмотреть рубрикатор, выставить студенту оценку по критерию (дата и комментарий - по желанию), посмотреть оценки студента, исправить или отменить оценку, посчитать итог по всем студентам, сменить правило итога и экспортировать итог в CSV. Дробные числа можно вводить с точкой или запятой, дату - в формате ДД.ММ.ГГГГ. Пункт `0` завершает программу.

Правила домена нарушить нельзя: оценка 12 из 10 отклоняется, как и оценка по критерию, которого нет в рубрикаторе. Итог нигде не хранится - он каждый раз считается из текущих оценок и рубрикатора в Domain Service, поэтому всегда согласован с ними. Экспорт пишется в файл `final_scores.csv` (имя задается при сборке контейнера).

## Структура проекта и слои

Выбрана архитектура **Ports and Adapters** (гексагональная). Зависимости направлены строго внутрь:

```text
cmd/pos ───> internal/app (DI-контейнер, composition root)
                 │
                 ├──> internal/adapters/console   ввод/вывод
                 ├──> internal/adapters/csvreport экспорт итога в CSV
                 ├──> internal/adapters/memory    хранилище в памяти
                 │
                 └──> internal/application        сценарии + порты (интерфейсы)
                            │
                            └──> internal/domain  сущности, VO, инварианты, Domain Service
```

- `internal/domain` - ядро: entity, value objects, агрегаты, фабрика оценок, Domain Service итога. Не знает про консоль, файлы и хранилище (в импортах - только стандартная библиотека).
- `internal/application` - сценарии "выставить оценку", "посчитать итог", "экспорт" и порты: `StudentRepository`, `RubricatorRepository`, `GradeBookRepository`, `FinalReportExporter`. Хранение снаружи домена.
- `internal/adapters` - инфраструктура: консольный UI, CSV-экспорт, хранилище в памяти. Реализуют порты и зависят только внутрь (application + domain).
- `internal/app` - DI-контейнер и единственная точка сборки графа зависимостей. Подмена реализации (например, хранилища или экспорта) делается здесь или в тестах.
- `cmd/pos` - запуск.

## Карта DDD

Ubiquitous language (слова заказчика -> типы кода):

| Термин        | Код                        |
|---------------|----------------------------|
| студент       | `domain.Student`           |
| критерий      | `domain.Criterion`         |
| рубрикатор    | `domain.Rubricator`        |
| оценка        | `domain.Grade`             |
| итог          | `domain.ScoringPolicy` (Domain Service) |

- **Entity:** `Student` - студент имеет устойчивый идентификатор `StudentID` и живет дольше оценок; `Grade` - факт выставления с ключом (студент, критерий), его можно исправить и отменить.
- **Value Object:** `Criterion` - неизменяемая тройка "название, максимум, вес" без идентификатора: два критерия с одинаковыми значениями неотличимы и равны. Пример из README - критерий "тесты, max 10, вес 0.3" в двух копиях это один и тот же критерий, а два студента "Иван" - два разных студента.
- **Агрегаты:** `Rubricator` хранит набор критериев (инвариант: уникальность названий); `GradeBook` хранит все оценки (инвариант: не больше одной оценки на пару студент-критерий, повторное выставление ее исправляет).
- **Инварианты** охраняются моделью, а не сервисами-проверялками: балл вне диапазона критерия и оценка по критерию вне рубрикатора не могут быть созданы вообще - их не пропускает фабрика оценок (`GradeFactory`); у критерия положительные максимум и вес; у студента непустое имя.
- **Repository (порт):** интерфейсы хранилища объявлены в `application/ports.go`, реализованы адаптером `adapters/memory`. Домен не знает, где лежат данные.
- **Domain Service:** итог не принадлежит ни студенту, ни оценке - он выводится из оценок и рубрикатора. Правило итога - `ScoringPolicy` в `domain/finalscore.go`; итог никогда не хранится и всегда считается из текущего набора оценок, поэтому не может разойтись с ним.

Модель не анемичная: `Rubricator.Add` отказывается от дубля критерия, `GradeBook.Put/Cancel` следят за уникальностью оценки, `GradeFactory` - единственная точка создания оценки с проверкой `score ∈ [0, max]` и связи с рубрикатором.

## Паттерны GoF

По одному из каждой группы, каждый закрывает конкретную боль:

- **Фабрика (порождающий)** - `domain.GradeFactory.Create`. Боль: создание оценки с инвариантами ("12 из 10" и "критерия нет в рубрикаторе") нельзя размазать по UI или сценариям - иначе появился бы второй путь создать оценку мимо правил. Приложение физически не может создать `Grade` иначе, чем через фабрику.
- **Декоратор (структурный)** - `domain.RoundedPolicy` поверх любой стратегии итога. Боль: округление - требование отображения, а не свойство правила расчета; декоратор добавляет его, не меняя ни стратегии, ни вызывающий код, и в контейнере оборачивает обе стратегии.
- **Стратегия (поведенческий)** - `domain.ScoringPolicy` с реализациями `WeightedSumPolicy` (взвешенный по весам) и `AveragePolicy` (простое среднее). Боль: правило итога сменяемо, и его нельзя размазывать по расчетам; смена правила в консоли (пункт меню 10) меняет итог, не трогая сущности и сценарии.

Сознательно ограничены тремя паттернами: "три уместных паттерна из разных групп ценнее шести декоративных". Композиция стратегии и декоратора собирается в DI-контейнере: `NewRoundedPolicy(NewWeightedSumPolicy(), 2)`.

## Тесты

`internal/domain`: проверка инвариантов критерия и рубрикатора (дубли, максимум и вес), отказ фабрики на 12 из 10, отрицательном балле и неизвестном критерии, граничные баллы 0 и max, исправление и отмена оценки в `GradeBook`, оба правила итога и округляющий декоратор. `internal/app`: сквозной сценарий через DI-контейнер (добавление студентов и критериев, отказы на нарушении инвариантов, исправление и отмена, итог, смена стратегии, экспорт CSV) и консольный сценарий на строковом вводе/выводе.
